# Security, Privacy & Integrity Audit — 2026-08-11

Full findings from the pre-alpha audit. Four parallel component audits plus direct
verification. Preserved verbatim in substance so nothing is lost to conversation scrollback.

**Context at time of audit:** hosted Supabase project retired; database moved to local
PostgreSQL 16 (port 5434); no `auth` schema; **zero RLS policies**; a dev auth bypass
(`DEV_AUTH_BYPASS`) in place treating every request as one fixed admin user.

**Verification standard used:** claims were checked against code and the live database.
Where a finding is inherited from an agent and not independently re-verified, it is marked
`[unverified]`. Where two sources disagreed, it is marked `[disputed]` and left open.

## 0. THE GOVERNING PATTERN

> **The codebase documents a compliance and security posture it does not have.**

| File | Claims | Reality |
|---|---|---|
| `db/schema/audit.ts:8` | "6-year HIPAA retention compliance" | No retention code anywhere. HIPAA is US law; under GDPR indefinite retention is a *violation*, not compliance |
| `db/schema/gdpr.ts:27` | FK "added in migration SQL" | Never created — `grep REFERENCES drizzle/*.sql` returns zero hits for these tables |
| `lib/dal/consent.ts:47` | "Layer 3: RLS policy enforcement" | Zero RLS policies exist |
| `lib/auth/totp.ts:30` | MFA secret "encrypted at-rest" | Stored plaintext |
| `lib/security/encryption.ts:203` | Documents 5-step DEK rotation | `rotateDEK()` returns a new key without re-encrypting anything |
| `app/api/user/delete-account/route.ts` | Tells user data deleted in 30 days | Nothing ever deletes it |

Correcting false claims is urgent **independently** of building the missing controls,
because at present the code cannot be used to tell which protections are real.

## 1. AUTHENTICATION & SESSION

### CRITICAL

**A1. Middleware is disabled entirely in development.** `middleware.ts:27-29`
```ts
if (process.env.NODE_ENV === 'development') return NextResponse.next()
```
Returns before *everything*: security headers, CSP, HSTS, the API 401 gate, protected-path
redirects, admin gating, session-version checks. `.env` also sets `NODE_ENV=development`.
Consequences: auth gating **cannot be tested locally at all**; dev and production take
different paths, so gating first executes in production. One inherited env var from a
custom server, `tsx`, or docker `env_file` ships a fully ungated app.
*Fix:* delete the short-circuit. Security headers must always apply. Gate only the
session-synthesis branch, on `NODE_ENV !== 'production'` **and** an explicit flag.
**VERIFIED** — read directly at `middleware.ts:27-29`.

**A2. `DEV_AUTH_BYPASS` has no build-time or `NODE_ENV` guard.**
`lib/supabase/dev-user.ts:31`, `lib/supabase/server.ts:52`, `lib/supabase/client.ts:29`,
`middleware.ts:114`. Sole condition is the string `'true'`. If ever set in a deployed
environment, then for **every anonymous request**:
- `getUser()`/`getSession()` return a fixed admin (`00000000-0000-4000-8000-000000000001`)
  whose email defaults to a real `ADMIN_EMAILS` address → every `requireAdmin()` passes
- No login redirect, no API 401
- Session-version/global-logout explicitly skipped → revocation impossible
- `signInWithPassword`/`verifyOtp`/`exchangeCodeForSession` all return success with **no
  credential check** — the login form accepts any password
- `signOut()` clears nothing — you cannot log out
- `.from()` runs raw SQL as the Postgres owner with no RLS → full read/write on every
  table including `mfa_secret`, `data_encryption_key`, `api_keys`
- All users share one id → everyone sees and mutates the same data

*Fix (defence in depth):* build-time throw in `next.config.js` when
`NODE_ENV === 'production' && DEV_AUTH_BYPASS === 'true'`; `NODE_ENV !== 'production' &&`
at all four call sites so the branch is tree-shaken out; runtime assert at server start.

**A3. 18 of ~23 `/api/admin/**` routes have no authorization check.**
`grep -l requireAdmin app/api/admin/*/route.ts` returns **zero files**. Middleware's
`adminPaths = ['/admin', '/api/foods/pending']` uses `startsWith('/admin')` — an API path
is `/api/admin/...`, which does not match. Net effect: `/api/admin/**` is gated only by
"any session exists".
*Exploit:* any alpha signup issues `PATCH /api/admin/compound/<uuid>` and rewrites the
compound database all nutrition math depends on.
*Fix:* `requireAdmin()` as the first statement of every handler, **and** add `/api/admin`
to `adminPaths`. Middleware alone is not a boundary (see A1).

**A4. Admin *pages* rely solely on middleware.** `app/admin/compounds/page.tsx`,
`core-compounds/page.tsx`, `food-health/page.tsx` have no server-side check.
(`app/admin/approvals/page.tsx:24-32` does it correctly — use as the model.)
*Fix:* server-side `getUser()` + `isAdminUser()` + `redirect` in a shared
`app/admin/layout.tsx`.

### HIGH

**A5. Auth is functionally dead.** Every non-bypass path (`app/(auth)/actions.ts:52,116,
168,214,264,309`) calls the retired Supabase host. Bypass off → nobody can log in.
Bypass on → everybody is admin. There is no third state.
`lib/auth/jwt.ts`, `password.ts` exist but nothing calls them for login: `verifyToken` has
zero call sites; `password.ts` is validation-only (no hash-and-store, no compare-on-login);
`incrementSessionVersion` is called only from tests.

**A6. Live Supabase credentials in `.env`.** `SUPABASE_SERVICE_ROLE_KEY` and
`SUPABASE_ACCESS_TOKEN=sbp_...`. `.env` is gitignored, but these are unrotated long-lived
credentials in the working tree. The `sbp_` token is an **organization-level management
token**, not scoped to the dead project — "the project is gone" is not protection.
Both were also printed to a terminal during this session and exist in that transcript.
*Fix:* revoke both. Owner action.

**A7. Rate limiting fails open everywhere.** `lib/redis/rate-limit.ts:32-38,74-82,103-111`.
No Upstash config → `checkLoginRateLimit`/`checkPasswordResetRateLimit` always return
`allowed:true`. Login brute-force and reset-email flooding unthrottled. Redis errors also
fail open. *Fix:* require config in production; fail **closed** on auth endpoints.

**A8. MFA verify returns HTTP 200 `success:true` on a wrong code.**
`app/api/auth/mfa/verify/route.ts:106-112` — failure is buried in `data.valid`. Any caller
checking `res.ok` or `body.success` (the normal pattern) treats a failed MFA as passed.
No attempt limiter; 6-digit TOTP with `window:1` (~3 valid codes at a time) is
brute-forceable in minutes. *Fix:* 401 on invalid; per-user lockout after 5 failures.

**A9. MFA can be silently re-enrolled.** `app/api/auth/mfa/enable/route.ts:53-60`
overwrites `mfa_secret` and `mfa_backup_codes` unconditionally — no re-authentication, no
check that MFA is already enabled. A stolen session re-points MFA at the attacker and locks
the owner out. Secret stored cleartext. Backup codes are generated but `verifyBackupCode`
has **no route** — recovery is unimplemented and used codes are never consumed.

**A10. Session-version / global-logout is inert.** `middleware.ts:222-247` compares against
`user_metadata.session_version`, populated only by hosted Supabase. The check sits in a
`try/catch` that **swallows errors and allows the request** — a DB blip silently disables
revocation. Skipped entirely under the bypass.

**A11. Account-existence leak.** `actions.ts:168-186` (`resendOTP`) and `:60-65` (`signUp`)
return raw provider errors; `resetPassword:322-326` is correctly generic — the
inconsistency is what makes enumeration possible. No Zod validation in `actions.ts`; email
and password are raw `formData.get() as string` and can be `null` at runtime.

**A12. `signUp` stores the plaintext password in `user_metadata.temp_password`**
(`actions.ts:57-59`) — readable client-side from the session object.

### MEDIUM

- **A13.** `isPublicApi` uses `pathname.includes(p)` not `startsWith` (`middleware.ts:148`)
  — one new route away from an auth bypass.
- **A14.** `/auth/callback` open-redirect: `next` query param used unvalidated in
  `NextResponse.redirect(`${origin}${next}`)` (`app/auth/callback/route.ts:14,59`).
- **A15.** Profile creation is not atomic with sign-in — only the OAuth callback creates
  `user_profiles` + DEK. OTP sign-ins end up authenticated with **no profile row**.
- **A16.** `/api/auth/api-keys`: no input validation on `name`; the "max 5" query composes
  `.is()` and `.or()` incorrectly and undercounts; the Premium gate is commented out.
- **A17.** API keys are generated but never accepted — `validateApiKey` has zero call sites
  and no route reads an `X-API-Key` header. Do not sell this feature until it exists.

### LOW

- **A18.** `lib/auth/jwt.ts:19` — `JWT_SECRET` falls back to the literal
  `'your-secret-key-min-32-characters-long'`; docstring claims EdDSA, code uses HS256.
- **A19.** CSP allows `'unsafe-inline'` + `'unsafe-eval'`; `connect-src` still whitelists
  the retired `*.supabase.co`.
- **A20.** Password policy is 8 chars + upper/lower/digit with no breach-list check.

## 2. API AUTHORIZATION SURFACE

> **Correction to an earlier claim in this project's history:** a grep suggesting "44 of 91
> routes have no auth check" was **stale and wrong**. The `/ai/*` routes call
> `requireAdmin()`; `/foods/[foodId]/approve` calls `requireAdmin()`; `/ai/log-food` calls
> `getSession()`. The real problems are different, and worse in places the grep called clean.

### Highest-risk routes

| Route | Method | AuthN | AuthZ | Mutates | Risk |
|---|---|---|---|---|---|
| `/api/admin/compound/[id]` | PATCH | any user | **none** | yes | any user rewrites compound DB |
| `/api/admin/source-mapping` | PATCH | any user | **none** | yes | corrupts nutrient mappings globally |
| `/api/admin/verify-mappings` | PATCH | any user | **none** | yes | same |
| `/api/admin/sanity-check-food-compound` | POST | any user | **none** | yes | paid-API burn + DB writes |
| `/api/admin/health` | GET | yes | `user_metadata.admin` | no | self-escalatable; leaks infra state |
| `/api/admin/errors` | GET/DELETE | yes | `user_metadata.admin` | yes | same; wipes error log |
| `/api/admin/food-health/*` (5) | GET | **none** | none | no | anonymous DB stats |
| `/api/admin/compounds-analysis` | GET | **none** | none | no | anonymous |
| `/api/foods/pending` | GET | **none** | middleware only | no | moderation queue exposed |
| `/api/ai/log-food` | POST | `getSession` | owner | yes | unmetered Anthropic spend |
| `/api/jobs/[jobId]` | GET | yes | **none** | no | IDOR on job payloads |

### Findings

**B1. `user_metadata.admin` is a self-writable privilege flag.** `admin/health/route.ts:85`,
`admin/errors/route.ts:61,186`. In Supabase, `user_metadata` is writable by the user's own
client: `supabase.auth.updateUser({ data: { admin: true } })`. One browser-console call
promotes any user. *Fix:* delete these checks; never authorize on `user_metadata` — only
`app_metadata` (service-role-only) or a DB roles table.

**B2. 29 route files authorize on `getSession()` rather than `getUser()`** — including
`ai/log-food:35`, `daily-values:73,182,311`, all of `meals/*` and `symptoms/*`, and
`middleware.ts:124`. `getSession()` decodes the cookie without verifying against the auth
server; Supabase documents it as untrusted server-side. *Fix:* `getUser()` wherever a
decision depends on identity.

**B3. `/api/ai/log-food` has authentication but no spend limit.** `maxIterations: 6` per
request; rate limiting dead project-wide. One authenticated account can loop it and bill you
without bound. *Prompt-injection is bounded* — `create_composite`/`log_meal` re-validate
`food_id` as UUID and hard-pin `createdBy: userId` / `visibility: 'private'` (lines 163-192),
so injected text cannot write to another user's rows. Achievable abuse is junk in
`food_approvals` plus spend. *Fix:* Postgres-backed per-user budget with a hard monthly cap.

**B4. IDOR on `/api/jobs/[jobId]`** (`:88`) — fetches by id with no `userId` comparison.
Everywhere else the IDOR class is **clean**: `meals/[mealId]`, `meals/items/[mealItemId]`,
`symptoms/[symptomLogId]`, `symptom-definitions/[definitionId]`, `auth/api-keys/[id]` all
scope by `userId` in the WHERE clause.

**B5. String-interpolated SQL in `/api/admin/source-search:58-66`** — `sql.raw` with the
user pattern inlined. Not currently exploitable (table/column names come from a fixed
`ADAPTERS` map; quotes doubled at `:62`) but it is the only user-text-into-raw-SQL path.
By contrast `lib/supabase/dev-shim.ts` parameterizes correctly via `$n` + `quoteIdent`.

**B6. 65 route files return `error.message` to clients** — stacks are logged not returned
(good), but raw Postgres/Drizzle messages disclose table and column names.
*Fix:* shared `apiError()` returning a generic message + correlation id.

**B7. Zod coverage is 69/91 route files (76%).** Gaps are mostly admin GETs reading
`searchParams` directly, plus `ai/chat:15`, `user/profile`, `user/demographics` PATCH, and
`auth/mfa/*`.

**B8. `[RESOLVED 2026-08-11]` basePath handling in middleware.** Two audits disagreed on
whether `request.nextUrl.pathname` includes the `/nutri` basePath. **Settled empirically with
a production build + `next start`, bypass off:**

```
/nutri/dashboard         → 307 → /nutri/login?redirect=%2Fdashboard
/nutri/analysis          → 307 → /nutri/login?redirect=%2Fanalysis
/nutri/admin/food-health → 307 → /nutri/login?redirect=%2Fadmin%2Ffood-health
```

The `redirect` param is `/dashboard`, proving `pathname` inside middleware is `/dashboard`.
**Next.js DOES strip basePath.** Therefore:
- Page-level protection **works correctly** in production. The claim that it "silently does
  nothing" was **wrong**.
- `middleware.ts:137`'s check for a `/nutri/api/` prefix is **dead code** — harmless but
  misleading.
- **A3/F1 stands and is unaffected:** `adminPaths` uses `startsWith('/admin')`; an admin API
  path is `/api/admin/...`, which does not match. Unauthenticated callers get 401 from the
  generic API gate, but **any authenticated user reaches every admin API.**

### Recommended structural fix

Stop treating auth as per-handler discipline. Extend `lib/auth/api-guard.ts` into:

```ts
withAuth(handler, { role: 'user' | 'admin', schema?: ZodSchema })
```

resolving the user via `getUser()`, checking `isAdminUser`, parsing input with Zod, applying
the budget check, and wrapping in a try/catch emitting sanitized errors — passing a typed
`{ user, input }` to the handler, which then *cannot* run unauthenticated. Add a CI lint rule
asserting every `app/api/**/route.ts` export is produced by `withAuth` (explicit
`withPublic()` for the genuinely public ones). This converts B1, B2, B3, B6, B7 and A3 from
91 individual judgement calls into one reviewed file plus a build-time check.

## 3. PRIVACY & GDPR

Jurisdiction: Norway (EEA). The app stores **Article 9 special-category health data**, which
carries a materially higher bar than ordinary personal data.

### LEGALLY BLOCKING FOR LAUNCH

**P1. CRITICAL — Right to erasure (Art. 17) is a stub. Nothing is ever deleted.**
`app/api/user/delete-account/route.ts:63-71` only INSERTs into `deletion_requests` with
`scheduled_deletion_at = now+30d`. **VERIFIED:** the only consumers of that table in app code
are the endpoint itself (create / check / cancel). No cron, no worker; `vercel.json` contains
only a redirect. The user is told their data will be deleted. It never is.
*Risk:* Art. 17 breach on Art. 9 data + a misleading statement to the data subject
(Art. 5(1)(a)). **Highest legal exposure in this audit.**

**P2. CRITICAL — Deletion would not cascade: five tables have NO foreign key.**

| Table | user column | FK? | Contents |
|---|---|---|---|
| `user_consent` | `user_id` | none | consent record |
| `api_keys` | `user_id` | none | key hashes, names |
| `audit_log` | `user_id` | none | IP, user-agent, activity |
| `deletion_requests` | `user_id`, `user_email` | none | plaintext email |
| `export_requests` | `user_id`, `user_email` | none | plaintext email |

The *cascading* side is correct — `meal_logs`, `symptom_logs`, `symptom_definitions`,
`daily_totals`, `favorite_foods`, `saved_meal_templates`, `ag_ui_logs`,
`user_custom_daily_values` all `onDelete: 'cascade'` to `user_profiles.user_id`; the
`set null` uses on `foods.created_by` etc. are appropriate.
*Fix:* add FKs or explicit deletes in the erasure transaction. `audit_log` should retain the
row but NULL `user_id`/`ip_address`/`user_agent`.

**P3. CRITICAL — Right of access/portability (Art. 15, 20) is a stub.**
`app/api/user/export/route.ts:45-52` inserts an `export_requests` row and promises a download
"within 5 minutes". Collection, generation, upload and email are all TODO comments;
`download_url` is never populated. `encryptForExport()` has **zero callers**. Statutory
one-month response deadline cannot be met.

**P4. CRITICAL — Health data is entirely plaintext; the DEK system is built-but-unused.**
**VERIFIED:** `encryptPHI`/`decryptPHI` have **zero callers** in app code — only their own
test file and the barrel re-export. `generateDEK` is called twice, purely to satisfy a
NOT NULL column.

Article 9 columns, all plaintext: `user_profiles.biological_sex`, `.life_stage`
(**NONE/PREGNANT/LACTATING — pregnancy status**), `.birth_date`; `symptom_logs.intensity/
.notes/.date`; user-scoped `symptom_definitions.name/description`; `meal_logs` +
`meal_items.notes`; `daily_totals.compounds`; **`ag_ui_logs.raw_input` (verbatim user free
text)**; `user_custom_daily_values.value/note`.
Ordinary personal data, plaintext: `full_name`, `avatar_url`, `waitlist_signups.email`,
`deletion_requests.user_email`, `export_requests.user_email`, `audit_log.ip_address/
.user_agent`.
Properly hashed: `api_keys.key_hash`, `mfa_backup_codes` (bcrypt).
**Plaintext secret: `user_profiles.mfa_secret`** — defeats the second factor for anyone with
DB read access.

**P5. CRITICAL — Key management defeats itself.** `db/schema/users.ts:15` —
`data_encryption_key` is a column *on `user_profiles`*, with no KEK, no envelope encryption,
no KMS. Anyone who can read the row reads both ciphertext and key. `rotateDEK()` is a no-op.
`db/seed/users.ts:63` sets the DEK to `crypto.randomUUID()` — not valid base64 for 32 bytes,
so `importDEK` would throw for every seeded user.
*Consequence:* the encryption in P4, if switched on as-is, would not protect against the
realistic threat (DB compromise), and would not qualify as an Art. 32 safeguard or an
Art. 34 breach-notification exemption.

**P6. HIGH — User free text goes to third parties with no legal basis, notice, or DPA.**
- `ai/log-food:79-140` → verbatim meal-description chat + history → Anthropic
- `ai/clarify:60-62`, `ai/smart-search:458-470` → user queries → Anthropic
- `ai/smart-search:565+` fans the **raw user query** to ~17 external government food APIs
  (US/Canada/Japan/Korea/India)
- No `user_consent` flag gates any of it; `third_party` exists in the schema but is never
  read on these paths

*Risk:* Art. 6 (no basis) + Art. 9(2) (no explicit consent) + Art. 28 (no processor
agreement) + Chapter V (transfers).
*Fix:* execute Anthropic's DPA/SCCs; name Anthropic in the privacy policy; gate AI behind
explicit Art. 9 consent; **send only the extracted food token to external food APIs, never
the user's sentence** — those lookups never need free text.

**P7. HIGH — Zero compliance artefacts exist.** No privacy policy, ToS, cookie/consent
banner, Art. 30 processing record, DPAs (Anthropic, Stripe, Resend, Upstash, UploadThing all
present in `.env`), or Art. 33/34 breach procedure.
**A DPIA is mandatory under Art. 35(3)(b) *before* processing begins** — large-scale
special-category data; Datatilsynet's mandatory list covers health tracking.
Also: keep insights descriptive, not diagnostic, to avoid drifting into MDR
software-as-medical-device territory.

**P8. HIGH — Consent lacks required granularity and evidentiary quality.**
`user_consent` is five booleans on one mutable row with a single `updated_at`. Art. 7(1)
requires the controller to *demonstrate* consent: per type, with timestamp, policy version
and mechanism. Overwriting destroys the history.
**There is no consent flag for the Art. 9 health processing itself** — the one consent you
cannot legally operate without. Withdrawal cleanup is a TODO, so withdrawing `research` or
`thirdParty` has no effect.
*Fix:* append-only `consent_events` table (user, type, granted, timestamp, policy_version,
ip, method); add `health_data_processing`; wire withdrawal to real cleanup.

**P9. MEDIUM-HIGH — Audit log: unbounded retention, full IPs, fictional retention claim.**
No expiry job exists anywhere — `lib/dal/audit.ts` exposes only read functions. Full
un-truncated IPs are written by `lib/security/audit-logger.ts:96-102`. `anonymizeIP()` has
**zero callers** and is broken for compressed IPv6 (`'::1'` → `'::1::'`,
`request-metadata.ts:135-142`). `ag_ui_logs` documents 90-day retention with an index built
for it, but nothing deletes. `getUserConsent()` writes a READ audit row on **every consent
page load** — generating more personal data than it protects (Art. 5(1)(c)).

### GOOD PRACTICE / NOT BLOCKING

- **P10.** DAL comments claim RLS that does not exist (`consent.ts:47`,
  `user/profile/route.ts:41`). Application checks are now the *only* layer.
- **P11.** `deletion_requests.user_email` / `export_requests.user_email` duplicate email
  specifically to survive deletion — defensible, but needs its own retention period, or the
  erasure table becomes the thing preventing erasure.
- **P12.** `ai/log-food` lets the model create `visibility: 'public'` foods from user
  descriptions ("Mom's lasagna" becomes globally visible). Force `private` unless explicitly
  confirmed.
- **P13.** Schema supports `INFANT_0_6M`–`TEEN_14_18Y`. If under-16s can register, Art. 8
  parental consent applies (Norwegian digital-consent age: 13). Age-gate or build the flow.

## 5. DATA INTEGRITY — CONVERSION FACTORS

The admin conversion checker reports 246 flags. **221 are false positives**; the checker
compares units as raw text, so `µg` (U+00B5) vs `μg` (U+03BC) vs `ug` vs `UG` all read as
mismatches, as does a `/100g` suffix at equal magnitude.

| Category | Count | Real? |
|---|---|---|
| micro-sign / case variants | 136 | No — same unit |
| `g/100g`→`g`, `mg/100g`→`mg` | 60 | No — same magnitude |
| `μg DFE`, `mg NE`, `alfa-TE`, `mg-ATE` | 25 | Judgment — nutrient equivalence units |
| **Genuine magnitude errors** | **25** | **Yes** |

The 25 real ones:

| Group | Count | Correct factor | Confidence |
|---|---|---|---|
| FRIDA amino acids `mg/100g`→`g` | 13 | ×0.001 | certain — currently **1000× too high** |
| FRIDA Boron, Fluoride `µg/100g`→`mg` | 2 | ×0.001 | certain |
| FRIDA Salt `g/100g`→`mg` | 1 | ×1000 | certain — 1000× too low |
| DUKE `ppm`→`g` / `mg` | 6 | ×0.0001 / ×0.1 | confirm Duke's per-100g basis |
| FRIDA "NE"→`mg`, MEXT `'……g……'`→`g` | 2 | judgment / corrupted unit string | owner call |

**Sequencing note:** factors are applied at **read time** (`value * conversion_factor` in the
source clients), not baked in at import. Fixing them later retroactively corrects everything,
so this does not block loading food data.

## 8. TOP PRIORITY ACTIONS

## 9. STRUCTURE & DEAD CODE

**Method:** static import-reachability graph (`@/` alias + relative resolution, all
extensions, index resolution) seeded from every file in `app/` plus `middleware.ts`.
**274 of 365 files reachable → 93 unreachable.** Zero unresolved imports, so the graph is
complete for static imports.

### S1. The dead Supabase-HTTP cluster — 5,555 lines, safe to delete

`db/supabase-client.ts` (90), `db/drizzle-http-adapter.ts` (198), and 8 `db/seed/*-http.ts`
variants (compounds 1891, validation 1316, research 704, users 687, categories 312,
symptoms 285, interactions 276, index 98). Nothing in `app/`, `lib/`, `middleware.ts` or
`db/seed/index.ts` reaches any of it, **and it is non-functional regardless** — it targets
the retired hosted project.

Diffed against non-http twins after normalizing the import line: categories, research,
users, validation are **byte-for-byte identical**; interactions near-identical. Pure
copy-paste debt from an IPv6 workaround for a database no longer in use.

*Two exceptions → confirm list:* `db/seed/symptoms-http.ts` has **no non-http twin**
(deleting loses the only symptom seed data). `db/seed/seed-display-settings.ts` and

broken** against local Postgres — port, don't delete.

### S3. `lib/data/compounds.ts` — 26,508 lines / 799 KB, delete

Three verified reasons: (1) zero importers; (2) stale by 7× — its header says "all 2036

**`lib/data/core-compounds.ts` (1,318) is a different case — KEEP.** Reachable from `app/`,
recently modified, encodes the Core display hierarchy. Presentation config, legitimately code.

### S4. LIVE BUG — the import queue consumes into a void

**VERIFIED:** `app/api/foods/import/route.ts:93` and `import/batch/route.ts:203` enqueue into
`foodImportQueue`. `lib/queue/worker.ts:399` instantiates `foodImportWorker`, but **nothing
imports `worker.ts`** and there is **no npm script** to start it. Jobs are accepted and never
processed. This is a live bug, not dead code.
*Decision needed:* ship the worker (add a start script) or return 501 from the import routes
and delete `lib/queue/worker.ts` + `lib/etl/*` + `lib/validation/data-validator.ts` (~2,400).

### S5. Duplication — the 17 source clients

12 of the 17 `lib/services/*-client.ts` are near-identical ~230-line staging clients.
Normalized, `nevo-client.ts` vs `ciqual-client.ts` differ by **36 lines, ~24 of them
comments**. Real variation is three things: secondary name column, ID type, staging table
name — a config object, not a class.
The compelling evidence is `app/api/foods/route.ts`, which contains the **same 17-way source
dispatch chain twice** (fetch at 321–453, standardize at 624–898). Every new source costs a
230-line client plus two branches in a 1,254-line route.
A `SOURCE_REGISTRY: Record<string, StagingSourceConfig>` collapses ~2,760 lines to ~400.
The four genuinely distinct clients stay hand-written: `foodb` (719, parent/child), `duke`
(351, plant parts), `usda` (388, remote API), `cnf` (378).
**Highest-leverage refactor in the codebase — but post-launch.** The duplication is stable
and not causing bugs.

### S6. Error-shape inconsistency

`'Unauthorized: Authentication required'` ×7, `'Unauthorized - please sign in'` ×3.

### S7. Structure verdict — do NOT start a new folder

The App Router layout is already conventional: route groups used properly, colocation
idiomatic, aliases match, `middleware.ts` correctly placed. No structural defect a rewrite
would fix.
**274 of 365 files are live** — a port means re-verifying 75% working code to remove 25% dead
code, during a multi-week freeze where "did I forget something?" has no cheap answer. The
dead code is *clustered* into three coherent groups, which is exactly the condition where
in-place removal wins. Every deletion is a `git rm`, independently revertible, with
`npm run build` as the check.
Two real nits: two component roots (resolved by S2), and 15 loose root files.
